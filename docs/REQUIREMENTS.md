# OpenCode Prompt Recorder Plugin — Requirements Document

## 1. Project Overview

### 1.1 Project Name
OpenCode Prompt Recorder Plugin

### 1.2 Project Type
OpenCode Plugin (TypeScript/JavaScript)

### 1.3 Core Feature Summary
An OpenCode plugin that automatically records each conversation's prompt, model, agent call chain, duration, and token usage to daily Markdown files. The plugin captures the complete lifecycle of user-assistant interactions and provides visibility into AI usage patterns, token consumption, and agent workflow execution.

### 1.4 Target Users
- OpenCode users who want to track their AI usage and conversation history
- Developers who need to analyze conversation patterns and optimize prompts
- Teams monitoring token consumption, costs, and agent performance
- Researchers studying AI assistant behavior and workflow efficiency

## 2. Functional Requirements

### 2.1 Core Features

#### F1: Automatic Conversation Logging
**Description**: Automatically record each user-assistant conversation to Markdown files after the conversation ends.

**Trigger Conditions**:
- User sends a message (captured via `chat.message` hook)
- Assistant message completes with token statistics available (captured via `message.updated` event)
- Session goes idle (captured via `session.idle` or `session.status (type=idle)` events)

**Output**: Write to `<project>/.opencode/prompts/opencode-prompt-YYYY-MM-DD_<sessionID>.md`

**Data Captured**:
- User prompt text
- AI model identifier
- Agent call chain
- Processing duration (total + per-step)
- Token usage (input, output, cache read/write)
- Task description (extracted from assistant output)
- Cost calculation (when billing is configured)
- End time (when session completes)

#### F2: Agent Chain Tracking
**Description**: Record the complete agent call chain (e.g., `oracle → build → explore`).

**Scope**: Include both the first-called agent and sub-agents invoked through other agents.

**Data Source**:
- `input.agent` from chat.message hook
- `output.parts` array with agent and subtask types

**Extraction Logic**:
- Direct agent invocation: `{ type: 'agent', name: 'agentName' }`
- Sub-task through agent: `{ type: 'subtask', agent: 'agentName' }`

**Merge Logic**: Initial agents merged with extracted agents, deduplicated while preserving order

**Output Format**: Arrow-separated string (e.g., 'oracle → build → explore')

#### F3: Token Statistics
**Description**: Record detailed token usage information for each conversation.

**Fields**:
| Field | Description |
|-------|-------------|
| Input Tokens | Total input token count (includes cached portions) |
| Output Tokens | Total output token count generated by the assistant |
| Cache Read | Tokens read from cache (billed at discount) |
| Cache Write | Tokens written to cache (billed at premium) |
| Uncached Tokens | inputTokens - cacheRead - cacheWrite |
| Cached Tokens | cacheRead + cacheWrite (subset of inputTokens) |

**Data Sources**:
- Primary: `info.tokens` structure (input, output, context, cache.read, cache.write)
- Fallback: `info.usage` structure (prompt_tokens, completion_tokens, cache_read_input_tokens, cache_creation_input_tokens, input_tokens, output_tokens)

**Extraction Logic**:
- Extract from `info.tokens.input` and `info.tokens.output`
- Fallback to `info.usage.prompt_tokens/completion_tokens` or `info.usage.input_tokens/output_tokens`
- Handle both new and legacy data structures

#### F4: Duration Tracking
**Description**: Record the processing duration of each conversation from start to completion.

**Two Duration Types**:
1. **Total Duration**: End time - Start time (entire session)
2. **Per-Step Duration**: Time between consecutive step completions

**Calculation**: Duration in seconds, fixed to 2 decimal places

**Start Time Capture**:
- Captured when user sends message
- Source: `chat.message` hook trigger timestamp

**End Time Capture**:
- Captured when session goes idle
- Source: `session.idle` or `session.status (type=idle)` event trigger timestamp

**Per-Step Duration Calculation**:
- Tracks `lastStepEndTime` in SessionState
- Step duration = Current step end time - lastStepEndTime
- `lastStepEndTime` updated after each step logs

**Output Format**: String with 2 decimal places (e.g., "12.34")

#### F5: Daily File Archiving
**Description**: Automatically generate log files organized by date for easy retrieval and analysis.

**File Naming Convention**: `opencode-prompt-YYYY-MM-DD_<sessionID>.md`

**Session Handling**:
- Each session gets its own file
- Multiple turns in the same session append to the same file
- Files stored in `<project>/.opencode/prompts/` directory

**Directory Creation**: Automatically create `.opencode/prompts/` directory if not exists

#### F6: Real-Time Step Logging
**Description**: In agent workflows (e.g., Sisyphus Ultraworker), multiple assistant messages may complete within a single session. Each completed assistant message is logged as a "step" immediately.

**Behavior**:
- Each step logged immediately upon completion
- Provides real-time visibility into agent workflows
- Summary with accumulated totals written when session goes idle

**Step Information Captured**:
- Step number
- Message ID
- Agent name
- Model used
- Completion time (start → end time range)
- Duration (per-step, not total)
- Task description
- Token counts for this step (input/output/cache)

#### F7: Task Description Extraction
**Description**: Automatically extract a brief task description from assistant output.

**Extraction Priority**:
1. First meaningful line from accumulated text content
2. Info metadata fields (task, description, name, etc.)
3. AI response content structure
4. First segment of assistant's reply content
5. Skip generic model names and format prefixes

**Text Cleaning**:
- Remove trailing punctuation (`;:,.!?`)
- Maximum length: 120 characters
- Skip generic patterns: `unknown`, `opencode/`, `claude-`, `gpt-`, code block markers, etc.

**Data Source**:
- Text accumulated via `message.part.updated` events
- Stored by message ID in `messageTexts` Map

#### F8: Billing System
**Description**: Calculate and record cost for each conversation when model pricing is configured.

**Configuration**:
```json
{
  "billing": {
    "enabled": true,
    "models": [
      {
        "model": "opencode/sonnet-4",
        "input": 3.75,      // price per million input tokens
        "output": 15.0,     // price per million output tokens
        "cacheRead": 0.3,  // price per million cache read tokens
        "cacheWrite": 3.75 // price per million cache write tokens
      }
    ]
  }
}
```

**Cost Calculation**:
- Uncached input cost = (uncached input tokens / 1,000,000) × input price
- Output cost = (output tokens / 1,000,000) × output price
- Cache cost = cache read cost + cache write cost
- Total cost = input cost + output cost + cache cost

**Output Format**:
```markdown
- **Cost**: $0.0123 (input: $0.005, output: $0.007, cache: $0.0003)
```

#### F9: Save All Conversation Logs
**Description**: Optionally save complete conversation logs including all user inputs and assistant outputs to a separate file.

**Trigger**: When `saveAllLogs: true` in config

**Output File**: `<project>/.opencode/prompts/opencode-prompt-log-YYYY-MM-DD_<sessionID>.md`

**Data Captured**:
- All user inputs (not just the first prompt)
- All assistant outputs (full content, not just step metadata)
- Timestamps for each user input and assistant output
- Session start and end times

**File Format**:
```markdown
# All Logs

## Session: ses_abc123
**Start:** 10:30:15 | **End:** 10:35:30

---

### User Input #1 — 10:30:15
[Full user prompt]

---

### Assistant Output #1 — 10:30:20
[Full assistant response]

---

### User Input #2 — 10:31:00
[Second user prompt]

---

### Assistant Output #2 — 10:31:30
[Second assistant response]

---
```

**Implementation Notes**:
- User inputs collected during `chat.message` hook
- Assistant outputs collected during `message.part.updated` events
- File written once when session.idle fires
- Does not require token availability check (captures text as it streams)

### 2.2 User Interactions and Hooks

#### Hook: chat.message
**Purpose**: Capture user messages when sent, record initial session state.

**Actions Performed**:
1. Check if session with completed messages exists, write summary first before restarting
2. Extract prompt text from `output.parts` (filter for text-type parts)
3. Extract model information from `input.model` (supports object and string formats)
4. Build initial agent chain from `input.agent`
5. Extract additional agents from `output.parts` using agent-extractor
6. Store session state in memory (sessionStates Map)
7. Memory management: Keep most recent 100 sessions

**Data Stored in SessionState**:
- userMsgID, prompt, model, startTime, agentChain, sessionStartTime
- Accumulator fields: totalInputTokens, totalOutputTokens, totalContextTokens, totalCacheRead, totalCacheWrite
- Tracking fields: completedMessageIDs, stepCount, headerWritten, hasCompletedMessage
- Text collection field: messageTexts (accumulated text by step number)

#### Hook: event
**Purpose**: Monitor assistant message completion, session idle, and state transitions.

**Event Types Handled**:
| Event Type | Action |
|------------|--------|
| message.part.updated | Accumulate text content by message ID for task description extraction |
| message.updated | Process completed assistant message, write step log, accumulate tokens |
| session.idle | Write summary log with accumulated totals, cleanup session state |
| session.status (type=idle) | Fallback trigger for summary logging |

**message.part.updated Processing**:
- Filter for text-type parts
- Store accumulated text by `step-${stepCount + 1}` key

**message.updated Processing Logic**:
1. Validate message role is 'assistant'
2. Validate completion status: `info.time?.completed` flag
3. Validate token availability: check `info.tokens` or `info.usage` structure
4. Skip already-processed messages (using completedMessageIDs Set)
5. Extract tokens, agent, model information
6. Extract task description from accumulated text
7. Write step log immediately
8. Accumulate tokens into session totals
9. Update lastModel

**Completion Check Logic**:
- Check `info.time?.completed` flag
- Check primary token structure: `info.tokens.input > 0 && info.tokens.output > 0 && info.tokens.reasoning !== undefined`
- Or check fallback token structure: `info.usage.prompt_tokens > 0 && info.usage.completion_tokens > 0`
- Wait for both conditions before logging (prevents incomplete data)

### 2.3 Data Structures

#### SessionState (In-Memory)
```typescript
interface SessionState {
  userMsgID: string;           // Unique identifier for user's message
  prompt: string;              // User's prompt text
  model: string;               // AI model identifier (initial)
  startTime: number;           // Unix timestamp (ms) when session started
  agentChain: string[];        // Agent call chain array
  sessionStartTime: string;    // Date string (YYYY-MM-DD)
  completedMessageIDs: Set<string>;  // Processed message IDs to avoid double-counting
  totalInputTokens: number;     // Accumulated input tokens
  totalOutputTokens: number;   // Accumulated output tokens
  totalContextTokens: number; // Accumulated context tokens
  totalCacheRead: number;      // Accumulated cache read tokens
  totalCacheWrite: number;    // Accumulated cache write tokens
  lastModel: string;          // Model from most recent message (may differ from initial)
  hasCompletedMessage: boolean; // Whether at least one message completed
  stepCount: number;          // Number of completed steps
  headerWritten: boolean;      // Whether file header written
  messageTexts: Map<string, string>; // Accumulated text content by message ID
  lastStepEndTime: number;    // Unix timestamp (ms) for per-step duration calculation
  allUserInputs: string[];     // Collected user inputs for all-logs feature
  allUserInputTimes: string[]; // Timestamps for user inputs
  allAssistantOutputs: string[]; // Collected assistant outputs for all-logs feature
  allAssistantOutputTimes: string[]; // Timestamps for assistant outputs
  allLogsFilePath: string | null; // Log file path for all-logs (set on session idle)
}
```

```typescript
interface MessageStep {

```

### 2.4 Edge Cases

| Edge Case | Handling |
|-----------|----------|
| Long Responses | Plugin waits for token stats before writing (not just completion flag) |
| Memory Management | Maximum 100 sessions stored in memory, oldest removed when exceeded |
| No Session State | Skip logging if session state not found (may have been cleaned up) |
| Missing Tokens | Skip logging and wait for next event if token data unavailable |
| File Creation | Automatically create `.opencode/prompts/` directory if not exists |
| Model Format | Support both object format (providerID/modelID) and string format |
| Runtime Compatibility | Support both Bun and Node.js runtimes |
| Duplicate Steps | Use completedMessageIDs Set to avoid double-counting |
| Partial Data | Wait for both completion flag and token availability |
| Session Interruption | If session has completed messages, write summary before starting new |
| Missing Task Description | Use multiple fallback strategies, leave empty if all fail |
| Generic Model Names | Filter `opencode/`, `claude-`, `gpt-`, etc. from task description |
| Billing Model Not Configured | Skip cost calculation when model pricing is not configured |
| All-Logs Disabled | When `saveAllLogs: false`, only step metadata is logged (no full content) |
| All-Logs Empty Content | Only save entries with non-empty trimmed content |

## 3. Non-Functional Requirements

### 3.1 Performance
- Minimal impact on OpenCode response time
- Asynchronous file writing (non-blocking)
- Efficient memory usage (max 100 sessions)
- Fast token extraction from message info
- Bun runtime optimization (utilize Bun.file and Bun.write)

### 3.2 Reliability
- Error handling for file write failures
- Fallback logging to file when OpenCode client logging unavailable
- Session state cleanup after successful logging (prevents memory leaks)
- Graceful degradation when data is incomplete
- Silent handling of logging failures (does not affect plugin main functionality)

### 3.3 Compatibility
- OpenCode Plugin API (primary)
- Bun runtime (primary, optimized)
- Node.js runtime (fallback)
- TypeScript strict mode

### 3.4 Maintainability
- Clear module separation (index, types, utils)
- Comprehensive JSDoc comments
- Type-safe interfaces for all data structures
- Unit tests for core utilities (Bun test)
- Code formatting (Prettier)
