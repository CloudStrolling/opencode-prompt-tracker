# OpenCode Prompt Log Plugin — Requirements Document

## 1. Project Overview

### 1.1 Project Name
OpenCode Prompt Log Plugin

### 1.2 Project Type
OpenCode Plugin (TypeScript/JavaScript)

### 1.3 Core Feature Summary
An OpenCode plugin that automatically records each conversation's prompt, model, agent call chain, duration, and token usage to daily Markdown files. The plugin captures the complete lifecycle of user-assistant interactions and provides visibility into AI usage patterns, token consumption, and agent workflow execution.

### 1.4 Target Users
- OpenCode users who want to track their AI usage and conversation history
- Developers who need to analyze conversation patterns and optimize prompts
- Teams monitoring token consumption, costs, and agent performance
- Researchers studying AI assistant behavior and workflow efficiency

## 2. Functional Requirements

### 2.1 Core Features

#### F1: Automatic Conversation Logging
**Description**: Automatically record each user-assistant conversation to Markdown files after the conversation ends.

**Trigger Conditions**:
- User sends a message (captured via `chat.message` hook)
- Assistant message completes with token statistics available (captured via `message.updated` event)
- Session goes idle (captured via `session.idle` event)

**Output**: Write to `<project>/.opencode/prompts/opencode-prompt-YYYY-MM-DD_<sessionID>.md`

**Data Captured**:
- User prompt text
- AI model identifier
- Agent call chain
- Processing duration
- Token usage (input, output, context, cache read/write)

#### F2: Agent Chain Tracking
**Description**: Record the complete agent call chain (e.g., `oracle → build → explore`).

**Scope**: Include both the first-called agent and sub-agents invoked through other agents.

**Data Source**:
- `input.agent` from chat.message hook
- `output.parts` array with agent and subtask types

**Extraction Logic**:
- Direct agent invocation: `{ type: 'agent', name: 'agentName' }`
- Sub-task through agent: `{ type: 'subtask', agent: 'agentName' }`

**Output Format**: Arrow-separated string (e.g., 'oracle → build → explore')

#### F3: Token Statistics
**Description**: Record detailed token usage information for each conversation.

**Fields**:
| Field | Description |
|-------|-------------|
| Input Tokens | Total input token count consumed by the conversation |
| Output Tokens | Total output token count generated by the assistant |
| Context Tokens | Context token count (separated from total input) |
| Cache Read | Tokens read from cache for context |
| Cache Write | Tokens written to cache for future use |

**Data Sources**:
- Primary: `info.tokens` structure (input, output, context, cache.read, cache.write)
- Fallback: `info.usage` structure (prompt_tokens, completion_tokens, etc.)

**Extraction Logic**:
- Extract from `info.tokens.input` and `info.tokens.output`
- Fallback to `info.usage.prompt_tokens` / `info.usage.completion_tokens`
- Handle both new and legacy data structures

#### F4: Duration Tracking
**Description**: Record the processing duration of each conversation from start to completion.

**Calculation**: `End Time - Start Time` (in seconds, fixed to 2 decimal places)

**Start Time Capture**:
- Captured when user sends message
- Source: `chat.message` hook timestamp

**End Time Capture**:
- Captured when assistant response completes
- Source: `message.updated` event timestamp

**Output Format**: String with 2 decimal places (e.g., "12.34")

#### F5: Daily File Archiving
**Description**: Automatically generate log files organized by date for easy retrieval and analysis.

**File Naming Convention**: `opencode-prompt-YYYY-MM-DD_<sessionID>.md`

**Session Handling**:
- Each session gets its own file
- Multiple turns in the same session append to the same file
- Files stored in `<project>/.opencode/prompts/` directory

**Directory Creation**: Automatically create `.opencode/prompts/` directory if not exists

#### F6: Real-Time Step Logging
**Description**: In agent workflows (e.g., Sisyphus Ultraworker), multiple assistant messages may complete within a single session. Each completed assistant message is logged as a "step" immediately.

**Behavior**:
- Each step logged immediately upon completion
- Provides real-time visibility into agent workflows
- Summary with accumulated totals written when session goes idle

**Step Information Captured**:
- Step number
- Agent name
- Model used
- Completion time
- Duration
- Token counts for this step

### 2.2 User Interactions and Hooks

#### Hook: chat.message
**Purpose**: Capture user messages when sent, record initial session state.

**Actions Performed**:
1. Extract prompt text from `output.parts` (filter for text-type parts)
2. Extract model information from `input.model` (supports object and string formats)
3. Build initial agent chain from `input.agent`
4. Extract additional agents from `output.parts` using agent-extractor
5. Store session state in memory (sessionStates Map)
6. Memory management: Keep most recent 100 sessions

**Data Stored in SessionState**:
- userMsgID, prompt, model, startTime, agentChain, sessionStartTime
- Accumulator fields: totalInputTokens, totalOutputTokens, totalContextTokens, totalCacheRead, totalCacheWrite
- Tracking fields: completedMessageIDs, stepCount, headerWritten, hasCompletedMessage

#### Hook: event
**Purpose**: Monitor assistant message completion, session idle, and state transitions.

**Event Types Handled**:
| Event Type | Action |
|------------|--------|
| message.updated | Process completed assistant message, write step log, accumulate tokens |
| session.idle | Write summary log with accumulated totals, cleanup session state |
| session.status (type=idle) | Fallback trigger for summary logging |

**Completion Check Logic**:
- Check `info.time?.completed` flag
- Ensure token stats are available (`info.tokens` or `info.usage`)
- Wait for both conditions before logging (prevents incomplete data)

**Step Processing**:
- Validate message role is 'assistant'
- Skip already-processed messages (using completedMessageIDs Set)
- Extract tokens, increment step count, write step log
- Accumulate tokens into session totals
- Update lastModel from this message

### 2.3 Data Structures

#### SessionState (In-Memory)
```typescript
interface SessionState {
  userMsgID: string;           // Unique identifier for user's message
  prompt: string;              // User's prompt text
  model: string;               // AI model identifier (initial)
  startTime: number;           // Unix timestamp (ms) when session started
  agentChain: string[];        // Agent call chain array
  sessionStartTime: string;    // Date string (YYYY-MM-DD)
  completedMessageIDs: Set<string>;  // Processed message IDs to avoid double-counting
  totalInputTokens: number;    // Accumulated input tokens
  totalOutputTokens: number;   // Accumulated output tokens
  totalContextTokens: number;  // Accumulated context tokens
  totalCacheRead: number;      // Accumulated cache read tokens
  totalCacheWrite: number;     // Accumulated cache write tokens
  lastModel: string;           // Model from most recent message
  hasCompletedMessage: boolean; // Whether at least one message completed
  stepCount: number;           // Number of completed steps
  headerWritten: boolean;      // Whether file header written
}
```

#### MessageStep (Per Step)
```typescript
interface MessageStep {
  stepNumber: number;          // Step number (1-based)
  messageID: string;           // Unique message identifier
  agent: string;               // Agent name for this step
  model: string;               // Model used for this step
  time: string;                // Formatted time (HH:MM:SS)
  duration: string;            // Duration in seconds
  inputTokens: number;         // Input tokens for this step
  outputTokens: number;        // Output tokens for this step
  contextTokens: number;       // Context tokens for this step
  cacheRead: number;           // Cache read tokens for this step
  cacheWrite: number;          // Cache write tokens for this step
}
```

#### LogData (For Summary Writing)
```typescript
interface LogData {
  sessionID: string;           // Session identifier
  time: string;                // Formatted time (HH:MM:SS)
  agentChain: string;          // Agent chain (arrow-separated)
  model: string;               // AI model identifier
  prompt: string;              // User's original prompt
  duration: string;            // Duration in seconds
  steps: number;               // Number of completed steps
  inputTokens: number;         // Total input token count
  outputTokens: number;        // Total output token count
  contextTokens: number;       // Total context token count
  cacheRead: number;           // Total cache read tokens
  cacheWrite: number;          // Total cache write tokens
}
```

### 2.4 Edge Cases

| Edge Case | Handling |
|-----------|----------|
| Long Responses | Plugin waits for token stats before writing (not just completion flag) |
| Memory Management | Maximum 100 sessions stored in memory, oldest removed when exceeded |
| No Session State | Skip logging if session state not found (may have been cleaned up) |
| Missing Tokens | Skip logging and wait for next event if token data unavailable |
| File Creation | Automatically create `.opencode/prompts/` directory if not exists |
| Model Format | Support both object format (providerID/modelID) and string format |
| Runtime Compatibility | Support both Bun and Node.js runtimes |
| Duplicate Steps | Use completedMessageIDs Set to avoid double-counting |
| Partial Data | Wait for both completion flag AND token availability |

## 3. Non-Functional Requirements

### 3.1 Performance
- Minimal impact on OpenCode response time
- Asynchronous file writing (non-blocking)
- Efficient memory usage (max 100 sessions)
- Fast token extraction from message info

### 3.2 Reliability
- Error handling for file write failures
- Fallback logging to file when OpenCode client logging unavailable
- Session state cleanup after successful logging (prevents memory leaks)
- Graceful degradation when data is incomplete

### 3.3 Compatibility
- OpenCode Plugin API (primary)
- Legacy activate API (fallback)
- Bun runtime (primary, optimized for)
- Node.js runtime (fallback)
- TypeScript with full type definitions

### 3.4 Maintainability
- Clear module separation (index, types, utils)
- Comprehensive JSDoc comments
- Type-safe interfaces for all data structures
- Unit tests for core utilities

## 6. Acceptance Criteria

### AC1: Basic Logging
- [ ] Each conversation is logged to a Markdown file
- [ ] File is created in `.opencode/prompts/` directory
- [ ] File naming follows pattern `opencode-prompt-YYYY-MM-DD_<sessionID>.md`

### AC2: Data Completeness
- [ ] All fields are recorded: time, model, agentChain, prompt, duration, tokens (input/output/context/cache read/cache write)
- [ ] Token counts match actual usage from message info
- [ ] Duration is accurately calculated (end time - start time)

### AC3: Agent Chain
- [ ] Primary agent from input context is captured
- [ ] Sub-agents from message parts are captured
- [ ] Agent chain is formatted as arrow-separated string

### AC4: Multi-Step Handling
- [ ] Each assistant message is logged as a separate step
- [ ] Steps are numbered sequentially
- [ ] Tokens are accumulated across steps
- [ ] Summary written after session idle

### AC5: Completion Handling
- [ ] Plugin waits for both completion flag AND token availability
- [ ] Long responses are logged correctly with full token stats
- [ ] No premature logging with incomplete data

### AC6: Error Handling
- [ ] File write failures are caught and logged
- [ ] Plugin does not crash OpenCode on errors
- [ ] Memory is properly cleaned up after logging

### AC7: Compatibility
- [ ] Works with Bun runtime
- [ ] Works with Node.js runtime
- [ ] TypeScript compiles without errors
